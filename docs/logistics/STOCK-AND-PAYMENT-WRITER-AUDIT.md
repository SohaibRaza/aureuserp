# Stock and payment writer audit — 2026-09-24

This report extends the [P0 execution record](P0-EXECUTION-REPORT-2026-09-23.md). It records source inspection, not executed concurrency evidence or production approval. Existing implementation behavior does not override the [target integration contracts](plan/05-INTEGRATION-CONTRACTS.md). The writer matrix describes the source inspected before the concurrent 2026-09-24 payment-registration and existing-quant transaction repairs. Their executed results belong in the newer P0 execution evidence; do not use this snapshot to assert that those local repairs are absent.

## Scope and limits

The inspected surface comprises Inventory balance, movement, reservation, count and scrap writers; Barcode operations and counts; Manufacturing completion and its move observer; Sales and Purchase procurement/receipt callers and registered listeners; Accounts payment registration, journal generation, posting, reconciliation and reversal; their API, Filament and Livewire entry points; and the specialized application Recon services.

Searches covered model hooks, service calls, `DB::` calls, explicit connections, transaction declarations, row locks, registered observers/listeners and queue interfaces under `app/` and the relevant plugin `src/` trees. Global searches for the balance and payment models were used to locate additional callers in Accounting and Invoices. These plugins expose inherited Accounts resources and InvoiceSummary behavior. Source references below are repository-relative, with the inspected line number; future changes can shift them.

This closes the bounded static caller inventory, not the runtime lock proof. It excludes operational database contents, triggers installed outside repository migrations, deployment-specific listeners, ad hoc SQL, external integrations and dynamically loaded third-party plugins. Uninstall cleanup and master-data setup were identified but are not certified safe by this audit. No database, payment or stock operation was executed for this report. Historical duplicate balances and orphan postings still require a read-only migration preflight on the intended deployment database.

## Corrections to the earlier report

The earlier report understated outer transaction coverage. `plugins/webkul/accounts/src/Filament/Resources/InvoiceResource/Actions/PayAction.php:33` explicitly enables database transactions. The Inventory availability, cancellation, confirmation and validation actions and the Manufacturing transition actions also enable them. The native Filament default is false (`vendor/filament/actions/src/Concerns/CanUseDatabaseTransactions.php:10`), but these actions override it.

Barcode validation is also wrapped in `DB::transaction` at `plugins/webkul/barcode/src/Livewire/Operation.php:402`. Barcode cancellation at line 395 delegates directly to Inventory. A transaction around one caller provides rollback for that caller; it does not establish a shared root lock, protect direct service callers, or serialize competing decisions.

## Connections, events, raw SQL and bypasses

- `DB::transaction` and Filament transaction helpers use the configured default connection. No explicit connection override was found in the inspected ordinary stock/payment model declarations. This is not proof that deployed connection resolution cannot differ. Transfer return is a notable explicit model-connection transaction. Tests must assert that command records, stock/ledger writes and locks use the same connection; reject unsupported cross-connection atomic work.
- Inventory operation events are dispatched synchronously from TransferWorkflow. Sales `Listeners/ComputeSaleOrderListener.php:12–19` and Purchase `Listeners/ComputePurchaseOrderListener.php:13–20` recompute their source orders. These listeners do not implement a queue interface. Manufacturing's Move observer writes availability immediately. Their writes join an existing transaction but have no independent rollback boundary.
- Accounts events trigger Sales/Purchase order recomputation. Sales `Listeners/ComputeSaleOrderFromMoveListener.php:55–63` also writes reversal invoice links through `DB::table()->updateOrInsert`. The payment event invokes `plugins/webkul/sales/src/Listeners/SendSMSNotificationListener.php:16–61` synchronously and may send customer/admin SMS before an outer transaction commits. A rolled-back or retried payment must not emit a misleading payment receipt. Defer external notification until commit and give retries a durable identity before claiming reliable delivery.
- Raw SQL searches found stock deletion in Inventory plugin uninstall (`InventoryServiceProvider.php:151`), setup/master-data writes, order-invoice pivot writes, and Recon-owned statement lifecycle writes. Many `DB::raw` matches are read aggregates; their presence is not evidence of a stock/ledger writer. No additional raw stock-balance posting job was located in the bounded scan. This negative result does not certify external SQL or dynamic plugins.
- Accounts `AccountServiceProvider.php:215–224` registers a wildcard saved listener for company-specific Partner/Product/Category properties. It does not serialize payments or residuals. Inventory product/UoM observers reject unsafe unit changes; their existence does not make every query-builder write run model hooks.
- Uninstall cleanup can remove stock records, and Manufacturing uninstall also examines ProductQuantity. Existing Logistics removal controls must remain in force. Module removal is not a financial/stock correction path.

## Bounded remediation and acceptance sequence

Existing issue numbers refer to `SohaibRaza/aureuserp`; do not close them from this report alone.

1. **#14 — canonical balance identity.** Inventory owner defines one supported identity including company/location/product/lot/package, audits duplicates read-only, and migrates without losing quantity or traceability. Acceptance: concurrent first creation produces one balance; null lot/package behavior passes on the project PostgreSQL baseline (ADR 0007); failure leaves the pre-migration state recoverable. Existing stock and package conversion policy must not be guessed during deduplication.
2. **#15 — reservation serialization.** After #14, lock/refetch move roots and candidate balances in one documented order; include MoveLine hooks and direct Barcode/form changes. Acceptance: two requests cannot reserve more than available stock, release cannot underflow the reservation, and cancellation racing an edit has one coherent result.
3. **#16 — completion, cancellation and returns.** Coordinate operation/move roots and every stock write on one connection. Acceptance: simultaneous complete/cancel gives one terminal result, repeated complete does not issue twice, and concurrent returns cannot exceed issued quantity. Inject a failure between source and destination writes and assert full rollback.
4. **#17 — bounded native customer returns; #18 — native issued-but-onsite stock correction.** Keep these as separate tasks because a customer return and an aborted factory departure have different physical facts. Apply the writer matrix to their affected Inventory paths. Acceptance includes original issue linkage, bounded quantity, no duplicate restoration, company isolation and no direct Logistics balance writes. This audit does not approve reversal policy or issued-but-onsite operational treatment.
5. **#19 — reconciliation fixture and regression repair.** Repair fixture ownership and signs without weakening accounting guards. Its independent-worker match test proves only its exercised bank-matching scenario, not ordinary payment registration or Inventory races.
6. **#20 — payment instruction identity.** Persist the significant payment intent and canonical result. Exact replay returns the original permitted result; changed intent conflicts. Keep identity separate from general invoice/partial-payment policy.
7. **#21 — shared payment atomicity and residual locking.** Give registrar, direct payment posting, reconciliation and corrections a documented shared transaction/lock contract. Acceptance: competing payments cannot both consume the same residual; a failed reconciliation leaves no orphan payment/journal/partial; a committed replay does not repost; notification occurs only after commit.
8. **#60 — scrap writer.** Build on #14–#16 where shared primitives are required. Preserve lot/package identity, prove repeat validation and simultaneous issue/scrap behavior, and inject failure during history creation.
9. **#61 — Manufacturing writer.** Coordinate production root with shared movement locks and observer effects. Acceptance: duplicate completion cannot consume or produce twice; failure after raw-material consumption restores all balances and order/work-order state; cancellation versus completion serializes.

These are implementation acceptance criteria, not observed failures. Static inspection identifies the unprotected decision windows; only an executed reproducer establishes an actual race outcome.

## Required concurrency evidence

Use independent database connections or worker processes, a barrier that proves both workers reached the competing decision, bounded timeouts, and persisted-state assertions after both workers finish. Record database engine/version and isolation level. A sequential retry test, SQLite run, skipped opt-in case, or worker fixture failure is not concurrency evidence.

| Scenario | Required persisted outcome |
| --- | --- |
| Two first receipts into the same missing balance | One canonical balance, sum of both receipts, two legitimate movement records. |
| Two reservations competing for one balance | Total reserved no greater than eligible available stock; each request has an explicit result. |
| Count application against simultaneous receipt/issue | The stale count is rejected or applied under the agreed serialized count rule; no silent lost movement. |
| Complete versus complete/cancel/edit | Exactly one valid terminal effect; source, destination, reservation and line state agree. |
| Two returns against the same issued quantity | Returned quantity never exceeds the allowable original quantity. |
| Scrap versus issue, and duplicate scrap validation | No double consumption; source/destination/history preserve product, lot, package and company. |
| Manufacturing completion versus cancellation/replay | Raw consumption and finished production occur at most once as one coherent operation. |
| Two payments against one obligation | Combined accepted payment consumption respects refreshed residual; losers fail or replan explicitly. |
| Two journal generations for one Payment | One linked journal, no orphan duplicate, valid balanced lines. |
| Reconcile versus unreconcile/reversal/bank match | Residuals, partials, full groups and bank provenance remain mutually consistent; no deadlock silently retried into a duplicate effect. |
| Fault after payment creation and before final reconciliation | No partial payment/journal/linkage survives; no pre-commit SMS is sent. |

Existing Inventory workflow tests cover many sequential reserve/release, lot, unit and scrap behaviors. `plugins/webkul/inventories/tests/Feature/Workflows/TransferIntegrityTest.php` is relevant sequential regression coverage. Sales has its own `OrderConfirmationConcurrencyTest.php`; its scope is order confirmation. `tests/Feature/Recon/MatchConcurrencyTest.php` supplies a real worker harness for one bank-matching scenario when enabled. None of those names or passing results establishes the entire matrix above. The parallel baseline work must record its executed results separately.

## Integrity implementation follow-up — 2026-09-24

The matrix above is a historical pre-repair snapshot. The current local changes add the following boundaries; they do not certify every native writer.

- `ProductQuantity::adjustStock` locks the product before reading or creating its exact balance identity. The PostgreSQL migration uses `UNIQUE NULLS NOT DISTINCT` across company, product, location, lot, package and stock owner (`partner_id`). Reservation changes are checked against the locked balance; releases cannot reduce reserved quantity below zero. This requires PostgreSQL 15 or later. Historical duplicates stop the migration for review rather than being silently merged.
- `Move::lockForStockMutation` obtains sorted product locks, then operation locks, then movement locks and reloads movement state. Product locks include the products in the affected parent operations. `MoveReserver`, `MoveCompleter`, `MoveCanceller`, transfer transitions and direct `MoveLine` save/delete use the common transaction boundary. A stale direct line edit is rejected. Product locking deliberately serializes mutations of the same product across locations; finer-grained locking requires separate contention evidence and a missing-row strategy.
- Transfer completion includes source and destination stock, picked state, backorders, operation state and synchronous callbacks in one transaction. Empty-balance cleanup is limited to affected products. Repeated completion cannot issue stock twice, but returning a persisted canonical command result remains future work.
- Automatic downstream reservation can discover an additional operation and product set after initial locks. A PostgreSQL deadlock must propagate through the whole command so all its changes roll back. Retry the complete command with fresh state; never retry only the downstream reservation. The implementation does not claim to eliminate every deadlock.
- Payment registration now persists the instruction result, locks source accounting documents and payment terms, and recalculates residual eligibility before posting. API and UI request identities are separate from register-row identities. Replay must be authorized and match the original intent. See the execution report for the scenarios actually verified.

Open work remains: count writers that directly assign quantities, scrap identity and replay (#60), Manufacturing order-level atomicity (#61), concurrent return bounds, release-precondition enrollment and canonical Inventory command results (#16–#18), and direct payment posting/reversal/reconciliation intersections (#21). Passing ordinary workflow tests for these modules does not prove their competing-writer safety.
