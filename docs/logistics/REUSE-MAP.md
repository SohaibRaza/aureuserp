Evidence baseline: `master` at `6d1f0db07ca3bd57455c11d06bb64151f59cc83f`. File references and claims marked inspected are against this commit. See `REPOSITORY-AUDIT.md` for method, lifecycle, risks, and open decisions.

The source-evidence column preserves what was found at the audited commit. Classification and integration-boundary text were reassessed on 2026-09-20 against later Phase 2A and Phase 2B evidence and the consolidated target plan; those reassessments are planning conclusions, not a fresh inspection of every cited file. Current implementation must use the canonical gap map and reverify source rather than infer a current decision from this derivative snapshot.

Classification:

- **REUSE**: use the existing owner and public workflow; do not duplicate it.
- **EXTEND**: existing capability is useful but logistics needs its own role/snapshot/contract around it.
- **MISSING**: no source-backed capability was found.
- **UNSAFE TO REUSE WITHOUT CHANGE**: using it directly would violate a stated invariant or create material data/control risk.
- **REFACTOR**: keep the owning module and business identity, but correct its shared service, schema, transaction, authorization, or lifecycle boundary before dependent Logistics use.
- **DECISION-GATED**: do not create a general-purpose master or editor until an approved business decision demonstrates that it is required.

## Consolidated target changes identified after the baseline audit

The earlier audit identified three immediate changes. The consolidated plan and later implementation evidence now require the following owner-correct work; the detailed source and acceptance mapping is in [`plan/07-AUREUSERP-GAP-AND-REFACTOR-MAP.md`](plan/07-AUREUSERP-GAP-AND-REFACTOR-MAP.md) and [`plan/08-IMPLEMENTATION-ROADMAP.md`](plan/08-IMPLEMENTATION-ROADMAP.md):

1. **Package-path-aware test bootstrap**: derive vendor plugin route/migration/install metadata from loaded packages.
2. **Sales commitment boundary**: retain atomic confirmation and add immutable commercial-quantity and packaging snapshots plus approved request identity where required.
3. **Inventory owner boundary**: correct quantity-record identity, reservation, completion, cancellation, returns, issued-onsite correction and direct-writer enforcement before Logistics dispatch relies on them.
4. **Accounts owner boundary**: correct instruction identity, payment recipient, residual locking, reconciliation, unknown outcomes, reversal and notification timing before Logistics freight settlement relies on them.
5. **Evidence and notification boundary**: use protected Logistics evidence for consequential records and real after-commit or durable-outbox behavior for notifications according to consequence.
6. **Lifecycle boundary**: extend operational suspension and uninstall protection as new records and obligations are added.

A generic Plugin Manager disable implementation remains optional and separately scoped. Logistics uses its company-scoped operational control and must retain read, receipt, correction, settlement and recovery access for existing obligations.

## Recommended regression gate

Before release, run focused logistics plus the existing Sales, Inventory, Accounts, Purchases, and Recon boundaries on fresh disposable MySQL 8 and PostgreSQL 16 databases. Passing source inspection is not a test result; no functional tests were executed in this audit.
